# 01 · Struct Skeleton (Python port)

Python port of `week1_baseline/ruby/01_struct_skeleton`. Defines the three
data structures that get passed around the agent loop for the rest of the
codebase:

- `boukensha.Tool`
- `boukensha.Message`
- `boukensha.Context`

Configuration (`boukensha.Config`, `boukensha.tasks`) is unchanged from
`00_config` — this iteration only adds the three structs above and a new
`examples/example.py` that exercises them together.

## Design considerations

Ruby represents these as lightweight `Struct`s — chosen there for being
lightweight and readable while learning, with plain classes as the
real-world alternative. The Python port follows the same split:

- `Tool` and `Message` are `@dataclass` — the idiomatic Python equivalent
  of a Ruby `Struct.new(...)`: auto-generated `__init__` and field
  declarations for a plain, mutable data record.
- `Context` stays a plain class with an explicit `__init__`, matching the
  Ruby reference's own choice to keep `Context` out of `Struct` — it holds
  behavior (`register_tool`, `add_message`, counters) and a required field
  (`task`), not just a flat tuple of values.

## Data Structures

### `boukensha.Tool`
| Field | Description |
|---|---|
| `name` | The name of the tool |
| `description` | Shown to the agent so it knows when to invoke the tool |
| `parameters` | The arguments that need to be passed in |
| `block` | The actual code that runs when the tool is called |

**Example:**
```
#<Tool name=move description=Move the player in a direction (north, so params=[:direction]>
```
(`params=` mirrors the Ruby reference's symbol-style formatting, e.g.
`[:direction]`, for output parity between the two ports.)

### `boukensha.Message`
A single unit of conversation between the user and the agent.

| Field | Description |
|---|---|
| `role` | Who is speaking — user, assistant, or tool_result |
| `content` | The text generated by the agent or provided by the user |
| `tool_use_id` | Links a tool result back to the specific tool call that requested it. The API requires this pairing to be exact. |

**Examples:**
```
#<Message role=user content=Explore north and tell me what you find....>
#<Message role=assistant content=Sure, let me head north and take a look....>
```

### `boukensha.Context`
Holds everything Boukensha needs to make an API call.

| Field | Description |
|---|---|
| `task` | The task class (e.g. `Player`) this context belongs to |
| `system` | Tells the agent what its job is. Kept separate from `messages`. |
| `messages` | The full conversation history, replayed on every turn |
| `tools` | The registered tools the agent is allowed to invoke, keyed by name |

**Example:**
```
#<Context task=player turns=2 tools=1>
```

## Code layout

| File | Purpose |
|------|---------|
| `boukensha/config.py` | `boukensha.Config` class (unchanged from `00_config`) |
| `boukensha/tasks/base.py` | abstract `Base` (unchanged from `00_config`) |
| `boukensha/tasks/player.py` | concrete `Player` (unchanged from `00_config`) |
| `boukensha/tool.py` | `boukensha.Tool` dataclass |
| `boukensha/message.py` | `boukensha.Message` dataclass |
| `boukensha/context.py` | `boukensha.Context` class |
| `boukensha/__init__.py` | top-level exports |
| `prompts/system.md` | default system prompt shipped with the library |
| `examples/example.py` | runnable smoke-test |

## Run

```bash
./week1_baseline/python/bin/01_struct_skeleton
```
(This runner is added in a later step, mirroring how the Ruby reference's
`bin/01_struct_skeleton` runner was added after its struct/example work.)

First run — set up the lesson-local virtualenv:

```bash
cd week1_baseline/python/01_struct_skeleton
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Then run the example directly:

```bash
.venv/bin/python examples/example.py
```

Expected output (values from your `.boukensha/`):

```
=== Boukensha Step 1: Struct Skeleton ===

Config:   #<Boukensha::Config dir=/home/mahdi/claude-code-camp-2026-Q2/.boukensha tasks=player>
Context:  #<Context task=player turns=2 tools=1>
Tool:     #<Tool name=move description=Move the player in a direction (north, so params=[:direction]>
Messages:
  #<Message role=user content=Explore north and tell me what you find....>
  #<Message role=assistant content=Sure, let me head north and take a look....>
```
